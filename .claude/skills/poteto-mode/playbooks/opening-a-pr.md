### Opening a PR

Invoked at the end of every other playbook.

**Worktree.** Work from a git worktree off main. Subagents without `isolation` inherit it. Multiple Agent calls on the same branch each get their own worktree (`isolation: "worktree"`), or `git fetch && git reset --hard origin/<branch>` between them. An isolated worktree starts from the default branch, so name the commit in the brief and have the agent check it out before it starts. Dirty branch with unrelated work: patch out, fresh worktree, apply. Snarled worktree: reset from main, redo minimally.

**Commits.** Commit liberally. Rebase into small, ordered commits before opening PRs. Each commit is a future PR: landable, ordered to tell the story. Amend when the fix belongs in a just-made commit. New commit when separable. Commit bodies don't restate the subject.

**PRs.** Run the slop strip (poteto-mode Non-negotiables) over the diff before commit and `/no-comments` before review. Write every PR title, description, and commit body with `/technical-writing` (every layer except Diátaxis, and apply the STE vocabulary rules: one word per action, keep articles, a plain verb over `-ing` where one works), then apply `/unslop`.

**Titles.** Conventional Commits `type(scope): subject`, no trailing period. Type such as `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, or `perf`. Scope is the area, such as `pstack` or `poteto-mode`. Subject is short, imperative, and names a real symbol when one carries the change, for example `fix(pstack): retarget opening-a-pr babysit trigger`.

**Descriptions.** The PR body is a one-minute briefing, not a lab notebook, for a reviewer who has the diff. It says why the change exists, what it leaves out, what it could break, and how you proved it works. Write short, simple sentences with few identifiers, no walls of text. This repository rebase-merges, so the body is not a commit message; keep it under about 40 lines anyway. Use `##` headings, not bold lead-ins, in this order, and drop a section with nothing to say:

- `## Why`: the problem and approach, 1–3 short sentences. No SHAs, rebase genealogy, or "based on main" preamble.
- `## What changed`: 1–3 short bullets. Name a real symbol or path only when it carries the change. Name both sides of a rename or retarget.
- `## Scope`: always. 1–3 short items on what it covers and what it deliberately leaves out (a follow-up, a known gap). No symbols, paths, or file-by-file essay.
- `## Tradeoffs`: only rejected alternatives a reviewer would otherwise ask about. Skip when there was no real choice.
- `## Blast Radius`: 1–2 sentences on who or what it touches and why that is safe or risky. If main is red, state the cost of leaving it red.
- `## Verification`: 1–3 bullets, each a real run path and its outcome. Perf: one primary number with its unit, `before → after`, and a link to the arena or swarm directory for the rest. No sample-size methodology, swarm recitals, or metric tables.

After the sections, attach videos or screenshots when they prove a claim. Full SHAs, swarm or arena lane recitals, lever-correction essays, file-by-file checklists, and "CLEAN" verdicts go in a linked artifact, not the body.

**Forge.** Pick the GitHub path before the first PR operation and keep that choice for create, edit, view, watch, and merge. GitHub CLI (`gh`) is the default. When `gh` is missing or not signed in, use the GitHub MCP tools and record the fallback. Do not require Graphite (`gt`).

Claude Code sessions block GitHub GraphQL with HTTP 403. So `gh pr view`, `gh pr checks`, `gh pr merge` and `gh api graphql` fail there, and other `gh pr` subcommands may too. In such a session, use these REST routes through `gh api`, or the matching GitHub MCP tools. The `ccr/` routes exist only behind that session's proxy, so outside it use `gh pr`, GraphQL or the MCP tools for threads, auto-merge and readiness.

- PR state. `GET repos/{owner}/{repo}/pulls/<pr>` returns `state`, `draft`, `merged`, `mergeable_state`, `head.sha` and `base.ref`. `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open&per_page=100'` lists all open PRs.
- Checks. `GET repos/{owner}/{repo}/commits/<sha>/check-runs`.
- Review threads. `GET repos/{owner}/{repo}/pulls/<pr>/ccr/review_threads` returns `resolved`, `outdated`, `path`, `line` and `comment_ids` per thread, with no author or body. Resolve one with `POST repos/{owner}/{repo}/pulls/<pr>/ccr/comments/<id>/resolve`.
- Comments with author and body, which the thread route lacks. `GET repos/{owner}/{repo}/pulls/<pr>/comments` returns each review comment with `id`, `user.login`, `body`, `path`, `line` and `pull_request_review_id`, and `in_reply_to_id` on a reply. `GET repos/{owner}/{repo}/pulls/<pr>/reviews` returns `id`, `user.login`, `state`, `body` and `commit_id`. `GET repos/{owner}/{repo}/issues/<pr>/comments` returns the conversation comments with `id`, `user.login`, `body` and `created_at`. Add `--paginate` past 30 items.
- Merge, pinned to a head. `gh api -X PUT repos/{owner}/{repo}/pulls/<pr>/merge -f merge_method=rebase -f sha=<head>`, or the MCP merge tool with `expectedHeadSha`.
- Auto-merge. `PUT` or `DELETE repos/{owner}/{repo}/pulls/<pr>/ccr/auto_merge`.
- Ready for review. `POST repos/{owner}/{repo}/pulls/<pr>/ccr/ready_for_review`.
- Create or retarget. `POST repos/{owner}/{repo}/pulls`, or `PATCH repos/{owner}/{repo}/pulls/<pr>` with `-f base=<branch>`.
- Issues. `GET repos/{owner}/{repo}/issues/<n>` reads one issue, or a PR as an issue, with `state`, `state_reason`, `assignees`, `labels`, `milestone` and `body`. `POST repos/{owner}/{repo}/issues` with `title`, `body`, `labels[]` and `milestone` (its number). `PATCH repos/{owner}/{repo}/issues/<n>` changes `body`, `title`, `milestone`, or `state` with `state_reason`. A PR is an issue for these routes and for assignees. `gh api --paginate 'repos/{owner}/{repo}/issues?assignee=<login>&state=open&per_page=100'` lists all that is assigned, PRs included.
- Assignees. `POST repos/{owner}/{repo}/issues/<n>/assignees -f 'assignees[]=<login>'` assigns, and `DELETE` on the same route with the same field unassigns. It starts no CI.
- Milestones. `GET` or `POST repos/{owner}/{repo}/milestones` with `title` and `description`, and `PATCH repos/{owner}/{repo}/milestones/<n>`.
- Dependencies and sub-issues. `POST repos/{owner}/{repo}/issues/<n>/dependencies/blocked_by -F issue_id=<id>` marks issue `<n>` blocked by another, and `DELETE repos/{owner}/{repo}/issues/<n>/dependencies/blocked_by/<id>` removes that. `POST repos/{owner}/{repo}/issues/<n>/sub_issues -F sub_issue_id=<id>` adds a child, and `DELETE repos/{owner}/{repo}/issues/<n>/sub_issue -F sub_issue_id=<id>` removes it. `<id>` is the other issue's `id` field, not its number.
- Refused in these sessions. The proxy answers `POST repos/{owner}/{repo}/statuses/<sha>` with 403, and check runs need a GitHub App token. An issue's `type` field is dropped without an error, through REST and the MCP tools alike, so leave issue types to the owner. Pinning an issue is browser only.
- Stacks. Send `-H "X-GitHub-Api-Version: 2026-03-10"`. `GET repos/{owner}/{repo}/stacks` lists stacks, each with `open` and its `pull_requests` (`number`, `state`); a PR that is in a stack also carries a `stack` object. Create one with `POST repos/{owner}/{repo}/stacks` and the body field `pull_requests`: 2 to 100 PR numbers, bottom to top, each PR's base ref equal to the previous PR's head ref (`-F 'pull_requests[]=<pr>'` once per PR). `POST repos/{owner}/{repo}/stacks/<stack_number>/add` puts more PRs on top. No route rebases a stack: the **Rebase stack** button is browser only. `gh stack submit` and `gh stack link` open PRs over GraphQL, so they fail in these sessions.
- Merge a stacked PR. `gh api -X PUT repos/{owner}/{repo}/pulls/<pr>/merge-async -H "X-GitHub-Api-Version: 2026-03-10" -f merge_method=rebase -f merge_action=direct_merge -f sha=<head>`. A `202` (new request) or `409` (one already pending) carries the request id at `.details.uuid`; poll a `409`'s request only if its `expected_head_sha`, `merge_method` and `merge_action` match yours. A `200` means the PR has already merged or is already queued. Poll `GET repos/{owner}/{repo}/pulls/<pr>/merge-async/<uuid>` until `.status` is `merged`, `failed` or `enqueued`; `enqueued` means a merge queue took it, not that it merged. The plain `/merge` route above cannot merge a stack, and an async merge of a stacked PR also merges every open PR below it.

**Size and stacks.** Prefer five narrow PRs to one large PR. In a repository with GitHub stacks, group dependent PRs into a stack through the stack routes in **Forge**. GitHub rebases and retargets the rest of the stack each time its bottom PR merges, but not when trunk moves ahead. Merge it bottom-up through the async route, and see the **Stacks** rules in the **kitimark-mode** skill, which also say who rebases a stack when trunk moves. The rest of this paragraph describes the hand-made chain, for a repository or a case without GitHub stacks. A stack is a base-branch chain. The root PR targets trunk. Each child branch rebases onto its parent's exact tip and its PR targets the parent branch. As a parent merges, move its child onto trunk per `playbooks/shipping.md` step 4. Create a child with `gh pr create --base <parent-branch>` and retarget one with `gh pr edit <pr> --base <parent-branch>`, or make the same calls through the **Forge** REST routes or the GitHub MCP tools. Branch from trunk only for independent work. Rebase on trunk before substantial stack work.

**Readiness.** Open every PR ready, never as a draft. With `gh`, omit `--draft`. Through the GitHub MCP tools, set `draft: false`. If a PR still opens as a draft, mark it ready through a **Forge** route or the MCP tools. Read the PR through a **Forge** route or the MCP tools before you refer to PR status.

**Babysit.** Opening a PR does not start a babysit. Post the URL and keep building. Finish the phase or stack first. Run a separate babysit pass only when the user asks for one after the whole stack exists. A babysit for each new PR stalls the build and spends checks on commits later waves restart. Push back when feedback drifts from intent.

A subagent that opens a PR runs the slop strip and `/no-comments`, and posts the URL. It returns to the parent without babysitting, unless its brief makes it the PR's owner, as Autopilot-full, Autopilot-stack and the **kitimark-mode** skill do. That owner's brief assigns the babysit loop and is the ask `playbooks/babysit.md` waits for. An Autopilot owner starts the loop after its code-ready report. A **kitimark-mode** owner opens the PR itself and carries it. Either owner reports merge-ready and is exempt from the rules here and in `playbooks/babysit.md` that hold babysitting until a whole stack is built.
