### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Pick the GitHub path, then verify each PR independently before it lands.** Use `gh` or the GitHub MCP tools per **Forge** in `playbooks/opening-a-pr.md`. Never require Graphite (`gt`). One verifier per PR, each a background subagent in its own worktree (`isolation: "worktree"`), runs the change the way a user would with the matching control skill (poteto-mode Non-negotiables), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare the id of the whole change, `git diff <merge-base> <sha> | git patch-id --verbatim`, at the verdict SHA and at the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR with a rebase merge pinned to its head, through the merge route in **Forge** (`playbooks/opening-a-pr.md`) or the GitHub MCP merge tool. In this repository the **kitimark-mode** skill decides who merges. A PR that needs `spec-approved` or touches a path its **What stays with the user** section names is the run's ceiling. Post its catch-up comment and stop there. A PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`merged` and `base.ref` from `GET repos/{owner}/{repo}/pulls/<pr>`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm GitHub auto-merge (the **Forge** auto-merge route) only on a PR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, retarget the PR whose base was the merged branch to trunk (the **Forge** retarget route), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's `git patch-id --verbatim` rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Watch the run under the `/loop` skill with one watcher on the current PR's merge state, such as `timeout 540 bash -c 'until <check>; do sleep 60; done'`, where the check reads `GET repos/{owner}/{repo}/pulls/<pr>` and succeeds when `merged` is true or `state` is `closed`. The `timeout` keeps each loop within the Bash timeout. Re-issue it for up to an hour, so a stalled merge comes back to you. Never wait in a background shell (`playbooks/babysit.md` step 6). A checks watcher can return before a queued merge lands. Re-read the current PR through **Forge** each time the watcher returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
