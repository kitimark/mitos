## Q1. Code-intelligence prior art: schema/identity models, extractor plugins, cross-repo linking, and mapping to Mitos provides/requires + evidence

### Takeaway
Every mature system splits the work into (1) per-language/per-unit **untrusted extractors** emitting typed facts into a **declared schema**, (2) a **global, location-independent identity scheme** (Kythe VName, SCIP symbol string, Glean `<name>/<hash>` DBs, purl/OSV ecosystem+name+version, Backstage entity refs), and (3) a **linking/derivation layer** that joins facts across units (Glean derived predicates, Kythe post-processing "cross-language linking", stack-graph path stitching, OTel span pairing). Mitos's provides/requires model is closest to Backstage `providesApi`/`consumesApi` and OTel client/server pairing for *what* is linked, and to Glean/Kythe/SCIP for *how* identities and facts are structured; none of them records per-edge assumption sets, which is Mitos's differentiator.

### Cited Findings

**GitHub CodeQL**
- CodeQL analysis is three steps: create a database, run queries, interpret results. "To create a database, CodeQL first extracts a single relational representation of each source file"; for compiled languages extraction works "by monitoring the normal build process" capturing AST plus "semantic data about name binding and type information"; for interpreted languages the extractor runs directly on source — [CodeQL docs: about-codeql.rst](https://github.com/github/codeql/blob/main/docs/codeql/codeql-overview/about-codeql.rst)
- "There is one extractor for each language supported by CodeQL"; multi-language codebases produce databases "one language at a time"; the database holds relational data, copied source files, and "a language-specific database schema, which specifies the mutual relations in the data" — [same](https://github.com/github/codeql/blob/main/docs/codeql/codeql-overview/about-codeql.rst)

**Meta Glean**
- Glean is "a system for working with facts about source code" (symbol locations, types, relationships, cross-references) queried with the Angle language; supported indexers: C/C++, Hack, Haskell, JS/Flow, Python, plus Rust/Go/TypeScript/Java/Python/.NET **via SCIP or LSIF** ingestion — [Glean README](https://github.com/facebookincubator/Glean/blob/main/README.md)
- Schema = predicates; "A predicate is the type of facts, which are the individual pieces of information that Glean stores"; predicates are schema-qualified (e.g. `example.Class`) and queries are patterns with variables joining facts across predicates — [Angle guide](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/angle/guide.md)
- **Derived predicates**: predicates "defined in terms of a query", either `stored` (materialized by `glean derive` before the DB is finished) or computed on demand; e.g. `predicate OutTarget.1 : {file, target} stored {F,T} where TargetOut {T,F}`; `if` cannot be used in stored derived predicates — [Glean derived predicates doc](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/derived.md); [Angle guide](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/angle/guide.md)
- A Glean DB has a **name** (usually the repo), a **hash** (e.g. the indexed revision), key-value **properties**, and the **schema stored in the DB**; `<name>/<hash>` uniquely identifies a DB; you can query with any schema compatible with the DB's — [Glean databases doc](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/databases.md)
- Incrementality: DBs are stacked; facts are owned by **units** (opaque strings, often filenames); an incremental DB stacked on a base can hide units, hiding the facts they own; Glean propagates units through the fact graph to compute **ownership sets**, and a **derived fact is visible only when the facts it came from are visible** (ownership expressions can grow large); one doc page said incremental derivation on stacked DBs was not yet implemented — [Glean incrementality doc (preview mirror)](https://deploy-preview-691--fb-oss-glean.netlify.app/docs/implementation/incrementality); secondary summary [sysdesign-wiki](https://sysdesign-wiki.pages.dev/concepts/stacked-immutable-databases/). (Secondary/mirror sources; official glean.software not reachable.)

**Google Kythe**
- Node identity is a **VName** ("Vector-Name"): node as a d-dimensional vector of semantic facts; initial 5 fields **Signature, Corpus, Root, Path, Language**; Signature is analyzer-opaque; Corpus is "loosely ... the contents of a given source repository" and Internet-accessible corpora "should generally prefer labels shaped like URLs"; Root distinguishes generated vs checked-in trees — [Kythe storage model](https://github.com/kythe/kythe/blob/master/kythe/docs/kythe-storage.txt)
- VNames are **extensible**: if new nodes collide, add dimensions; "updating existing VNames to a new projection is a trivial mechanical rewriting process" — [same](https://github.com/kythe/kythe/blob/master/kythe/docs/kythe-storage.txt)
- Pipeline includes a post-indexing stage for "Cross-language linking, precomputation of transitive closure relations, ... dependency injection" — [same](https://github.com/kythe/kythe/blob/master/kythe/docs/kythe-storage.txt)
- Schema has ~60 typed edge kinds (`defines/binding`, `ref`, `ref/call`, `ref/imports`, `childof`, `overrides`, `depends`, `satisfies`, ...); notably **`generates`** ("A generates B if A is related to B through some extralingual process", e.g. RPC IDL → C++/Java code, so one can "list all the C++ and Java uses of a particular service call, starting at the specification of that service") and **`imputes`** (anchor → semantic node via extralingual process) — [Kythe schema](https://github.com/kythe/kythe/blob/master/kythe/docs/schema/schema.txt)

**GitHub stack-graphs / tree-sitter-graph**
- Stack graphs "define the name resolution rules for an arbitrary programming language" without tapping into build tools; based on Eelco Visser's scope graphs; **"This repository is no longer supported or updated by GitHub"** (archived; fork to continue) — [stack-graphs README](https://github.com/github/stack-graphs/blob/main/README.md)
- Key insight: resolution keeps a **symbol stack** and **scope stack**, so resolving `A.foo` pauses `foo`, resolves `A`, resumes; "each 'chunk' of the overall graph only depends on 'local' information from the original source file (a.k.a., it's incremental!)" — non-incremental scope-graph approaches must mutate distant parts of the graph, "especially problematic for popular packages with lots of downstream dependencies" — [stack-graphs lib.rs docs](https://github.com/github/stack-graphs/blob/main/stack-graphs/src/lib.rs)
- `tree-sitter-graph` is "a DSL for constructing arbitrary graph structures from source code that has been parsed using tree-sitter" — [tree-sitter-graph README](https://github.com/tree-sitter/tree-sitter-graph/blob/main/README.md); `tree-sitter-stack-graphs` CLI indexes a folder into a DB and skips already-indexed files unless `-f` — [tree-sitter-stack-graphs README](https://github.com/github/stack-graphs/blob/main/tree-sitter-stack-graphs/README.md)

**Sourcegraph SCIP**
- Global symbol grammar: `<symbol> ::= <scheme> ' ' <package> ' ' (<descriptor>)+ | 'local ' <local-id>`, `<package> ::= <manager> ' ' <package-name> ' ' <version>` ('.' for empty); descriptors are suffix-typed (namespace `/`, type `#`, term `.`, method `(disambiguator).`, type-param `[name]`, param `(name)`, meta `:`, macro `!`) — [scip.proto](https://github.com/sourcegraph/scip/blob/main/scip.proto)
- Messages: `Index{metadata, documents, external_symbols}`, `Document{language, relative_path, occurrences, symbols}`, `Occurrence{range, symbol, symbol_roles bitset}`, `SymbolInformation{symbol, relationships, kind, enclosing_symbol...}`, `Relationship{symbol, is_reference, is_implementation, is_type_definition, is_definition}` — [scip.proto](https://github.com/sourcegraph/scip/blob/main/scip.proto)
- Cross-repo: non-local symbols are self-describing global strings so identity works across independently produced indexes; `external_symbols` is optional — "Leave this field empty if you assume the external package will get indexed separately" — [scip.proto](https://github.com/sourcegraph/scip/blob/main/scip.proto)

**Soufflé Datalog (provenance)**
- Soufflé provenance (Zhao, Scholz et al., 2019) generates per-rule "subproof" subroutines that search the computed DB backward; bottom-up evaluation yields **minimal-height proof trees**; interactive `explain`/`subproof` commands, plus `explainnegation` for absent tuples — [Provenance for Large-scale Datalog (arXiv 1907.05045)](https://arxiv.org/pdf/1907.05045) (via search summary; full text not fetched)

**OpenRewrite**
- OpenRewrite's **Lossless Semantic Tree (LST)** is "OpenRewrite's type-aware model of your source code, built in memory each time a recipe runs"; Moderne batch-builds and serializes LSTs "so they can be reused across repos"; OpenRewrite works "one repository at a time", Moderne runs recipes across thousands of repos; multi-tier licensing (some language parsers under Moderne Source Available License) — [openrewrite/rewrite README](https://github.com/openrewrite/rewrite/blob/main/README.md)

**deps.dev / OSV**
- deps.dev is a Google-hosted service for package structure/security; v3 API (stable) and v3alpha, JSON/HTTP and gRPC; package identity is `systems/{ecosystem}/packages/{name}` (e.g. `/v3/systems/npm/packages/%40colors%2Fcolors`) — [deps.dev README](https://github.com/google/deps.dev/blob/main/README.md)
- OSV `affected[].package` identifies packages by `ecosystem`, `name`, and optional `purl`, with `ecosystem_specific`/`database_specific` extension blocks — [OSV schema](https://github.com/ossf/osv-schema/blob/main/docs/schema.md)

**Backstage software catalog**
- Relations are directional typed triples with inverse pairs: `providesApi/apiProvidedBy` ("a component exposes an API ... hosts callable endpoints"), `consumesApi/apiConsumedBy` ("depends on endpoints of the API"), `dependsOn/dependencyOf`, `ownedBy/ownerOf`, `partOf/hasPart`; each "commonly generated based on `spec.providesApis` / `spec.consumesApis` / `spec.dependsOn`"; ownership "is not to be used by automated processes to for example assign authorization" — [Backstage well-known relations](https://github.com/backstage/backstage/blob/master/docs/features/software-catalog/well-known-relations.md)
- Provenance annotations: `backstage.io/managed-by-location` / `managed-by-origin-location` (where the entity descriptor was fetched from), `backstage.io/source-location`, `backstage.io/orphan` (entity whose origin no longer references it) — [Backstage well-known annotations](https://github.com/backstage/backstage/blob/master/docs/features/software-catalog/well-known-annotations.md)

**OpenTelemetry service graph**
- Service Graph Connector (traces → metrics, alpha) infers topology by pairing spans: client/server, producer/consumer (messaging), and client spans with `db.name`; unpaired spans held in an in-memory store until matched or TTL expiry; emits `traces_service_graph_request_total{client, server, connection_type}`; `virtual_node_peer_attributes` (default `peer.service.name, peer.service, db.name, db.namespace, db.system, db.system.name`) creates **virtual nodes** for uninstrumented peers; based on Grafana Tempo's service-graph processor — [servicegraphconnector README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/connector/servicegraphconnector/README.md)

### Inferences
- **Identity**: adopt a SCIP-like self-describing string for code symbols (scheme + manager + package + version + descriptors) and a Kythe-like extensible VName (`corpus`=repo URL, `root`, `path`, `language`, `signature`) for nodes; add Mitos-specific kinds for *service interfaces* (e.g. `http:<host-or-service-id>:<METHOD>:<route-template>`, `topic:<broker>:<name>`, `grpc:<pkg.Service/Method>`). Global, location-independent keys are what let per-repo extractors run in isolation and link later (SCIP/stack-graphs lesson).
- **Provides/requires join = Kythe `generates` + Backstage `providesApi/consumesApi` + OTel client/server pairing**: per-repo extractors emit half-edges (`provides(svc, iface)` / `requires(svc, iface)`); a trusted resolver joins them. The OTel "virtual node" concept maps to a `requires` with no matching `provides` (unresolved/external endpoint) — Mitos should represent these explicitly rather than drop them.
- **Glean's ownership sets are the nearest prior art to Mitos's per-edge assumption sets**: Glean tracks which *units* (files) each fact depends on and hides derived facts when sources are hidden. Mitos generalizes "unit" from file to *assumption* (rule, plugin, declaration, repo@rev). Glean's note that ownership expressions "can get arbitrarily large" warns that assumption-set labels need interning/hash-consing (Glean found "relatively few distinct ownership sets").
- **Stack-graphs' lesson**: make extraction strictly per-file/per-repo local with deferred stitching, so re-extraction of one repo never mutates another repo's facts; also, stack-graphs being archived is a caution against depending on it as a library.
- **Soufflé's minimal-height proof trees** are a ready model for Mitos's "evidence" view: each edge can carry (or lazily recompute) a derivation tree whose leaves are source spans + assumptions.
- CodeQL/Glean schemas being stored *with* the DB (Glean) suggests storing the Mitos fact schema version + plugin set hash in each snapshot.

## Q2. Proof-carrying / certificate-checking architecture patterns and assumption tracking

### Takeaway
The pattern Mitos needs is well established: an **untrusted producer** (AI-written plugin, SAT solver, compiler) emits an artifact plus certificate, and a **small trusted checker** validates it against a **consumer-owned policy/statement**. In Lean today this is concretely embodied by `leanchecker` (kernel replay of .oleans) and **Comparator** (sandboxed build, export, re-check against a reference "Challenge" statement with an axiom allowlist), now merged into Lean core as `lake comparator`/`lake check` per its README. ATMS labels (environments = sets of assumptions, nogoods) give the theory for per-edge assumption sets and precise retraction; `collectAxioms` is the in-Lean precedent.

### Cited Findings
- **PCC (Necula, POPL'97, pp. 106–119)**: consumer fixes a safety policy as inference rules; a VC generator turns untrusted code into a formula; producer supplies a proof; consumer checks it. The trusted base "includes only the checker"; producer tools are untrusted, "bugs will simply produce incorrect binaries that will be caught". Proofs encoded in Edinburgh LF so the checker is a small generic LF type-checker independent of the policy — [search summary of Necula's PCC pages](https://people.eecs.berkeley.edu/~necula/touchstone.html); [Necula Marktoberdorf notes](https://people.eecs.berkeley.edu/%7Enecula/Papers/marktoberdorf.pdf); Foundational PCC (Appel) — [fpcc.pdf](https://www.cs.princeton.edu/%7Eappel/papers/fpcc.pdf). (Details via search summary; the summarizer itself recommended verifying LF details against the 1997 paper.)
- **Certificate checking for SAT**: `cake_lpr` checks LRAT/LPR proofs, verified in CakeML/HOL4 "down to the level of its x64 machine code"; used to validate UNSAT proofs in the 2020 SAT Competition; DRAT inputs pre-processed by untrusted DRAT-trim into LRAT — [Tan, Heule, Myreen, TACAS 2021 (PMC)](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7984575/); [SAT competition 2024 checker doc](https://satcompetition.github.io/2024/downloads/checkers/cakelpr.pdf)
- **Same pattern inside Lean**: Lean's `bv_decide` (LeanSAT) ships an LRAT checker in `Std.Tactic.BVDecide.LRAT` — `def check (lratProof : Array IntAction) (cnf : CNF Nat) : Bool` — "the implementation of the LRAT checker as well as a proof that the given CNF is unsat if the checker succeeds" (external SAT solver = untrusted oracle) — [Lean source: Std/Tactic/BVDecide/LRAT/Checker.lean](https://github.com/leanprover/lean4/blob/master/src/Std/Tactic/BVDecide/LRAT/Checker.lean)
- **Lean's kernel-replay checker**: `lean4checker` "will replay the environment in <module>, starting from the environment provided by its imports, ensuring that the kernel accepts all declarations"; `--fresh` replays all constants into a fresh env; "not an external verifier, as it uses the Lean kernel itself" but detects "environment hacking, i.e. using metaprogramming facilities to build an inconsistent Lean Environment". The repo is deprecated: merged into Lean as **`leanchecker`, distributed with every toolchain from v4.28.0** (`lake env leanchecker [--fresh] <Module>`) — [lean4checker README](https://github.com/leanprover/lean4checker/blob/master/README.md)
- **Comparator** (gold standard for untrusted proofs): `Challenge.lean` holds reference statements with `sorry`; `Solution.lean` restates and proves them. For `theorem_names` it guarantees the solution proves "the same statement as provided in Challenge", uses only `permitted_axioms` (e.g. `propext`, `Quot.sound`, `Classical.choice`), and is kernel-accepted. `definition_names` checks name/type/universe levels/safety but "can be gamed" and need human review. Both are built with `lake` inside the **`landrun`** sandbox (read whole FS, write only `.lake` and `/dev`); `.olean`s exported via **`lean4export`** inside the sandbox and replayed; optional second kernel **nanoda** (Rust) or arbitrary `external_kernels`. Threat model: trust the Challenge import closure and lakefile, Lean kernel; don't run as privileged user; recommended `systemd-run` with `RestrictAddressFamilies=~AF_UNIX` against a landrun vulnerability. **"Comparator was merged into Lean core in v4.35.0 as `lake comparator` and `lake check`"** — [leanprover/comparator README](https://github.com/leanprover/comparator/blob/master/README.md)
- Comparator's export-then-parse step defeated an exploit that fooled lean4checker and SafeVerify (both use in-process `Environment.replay`) — [Zulip thread "SafeVerify-passing kernel soundness exploit" (Jan 2026, via search summary)](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/SafeVerify-passing.20kernel.20soundness.20exploit.html); SafeVerify — [Reservoir](https://reservoir.lean-lang.org/@GasStationManager/SafeVerify). The Lean Language Reference "Validating Proofs" chapter calls Comparator the gold standard and lists remaining assumptions (soundness of Lean's logic, comparator plumbing, sandbox) — [Lean reference: ValidatingProofs (via search summary)](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)
- **Axiom tracking in Lean**: `collectAxioms [Monad m] [MonadEnv m] (constName : Name) : m (Array Name)` walks the dependency closure (axioms add themselves; defs/theorems/opaques recurse into type and value; inductives into type and ctors), caching per-constant sorted axiom arrays, and uses a per-module precomputed `exportedAxiomsExt` so imported declarations don't need re-walking — [Lean source: Lean/Util/CollectAxioms.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Util/CollectAxioms.lean)
- **ATMS (de Kleer 1986, AI 28(2):127–224)**: each node gets a **label** = set of **environments**; an environment = set of assumptions; **nogoods** = minimal inconsistent environments; environments that are supersets of nogoods are removed from labels; supersets of nogoods are nogood; labels can blow up exponentially (compressed variants e.g. CATMS) — [arXiv 1107.0035](https://arxiv.org/pdf/1107.0035); [US patent 4918621](https://patents.google.com/patent/US4918621); [Extending the ATMS](https://www.academia.edu/121049762/Extending_the_ATMS); [arXiv 2407.06400](https://arxiv.org/pdf/2407.06400)
- **Datalog provenance** (Soufflé) gives minimal-height proof trees per derived tuple — [arXiv 1907.05045](https://arxiv.org/pdf/1907.05045)

### Inferences
- **Mitos = Comparator applied to plugins.** Framework-owned obligation statements play the role of `Challenge.lean` (trusted, versioned, small); the AI-written plugin is `Solution.lean`; Mitos checks (a) each obligation constant exists in the plugin with a type *definitionally/syntactically equal* to the framework statement, (b) `collectAxioms` ⊆ allowlist (reject `sorryAx`, `Lean.ofReduceBool`/native_decide-style axioms unless explicitly permitted and recorded as an assumption), (c) kernel acceptance via export + replay in a fresh process. The extractor *function* itself is like a Comparator "definition hole": its type can be checked, but its behavior beyond the proved obligations is an assumption to be recorded, not trusted.
- **LCF/oracle+checker split for the resolver**: the plugin (untrusted oracle) produces facts plus evidence (source spans, matched patterns); the trusted Lean core re-validates evidence where cheap (e.g. that the span text matches the claimed pattern), the way LRAT checkers re-validate solver output.
- **ATMS labels = per-edge assumption sets.** Each edge label is a set of environments (alternative justifications), each an assumption set {plugin@hash, rule-id, declaration-id, repo@rev}. Retracting an assumption deletes every environment containing it; an edge disappears only if its label becomes empty — precise impact analysis. Declaring "these two declarations conflict" = a nogood. Expect to need minimality + interning to keep labels small (cf. Glean ownership sets).
- `collectAxioms`' per-module precomputed cache is a template for incremental assumption-closure computation over plugin modules.

## Q3. Lean 4 plugin mechanics: loading, isolating, checking user modules

### Takeaway
A Lean host program can load user plugin modules in two ways: (1) **`Lean.importModules`** of compiled `.olean`s into an `Environment` (data-only, for inspecting `ConstantInfo` and checking types/axioms), optionally followed by **`evalConst`** to run code via the interpreter or precompiled native code; (2) **native shared-library plugins** (`Lean.loadPlugin` / `lean --plugin`, `loadDynlib` / `--load-dynlib`, Lake `plugins`/`dynlibs`/`precompileModules`) that run initializers on load. Both execute arbitrary code, and Lean never unloads libraries, so untrusted plugins must be built and executed in an external sandbox/separate process, with the trusted core only consuming exported data and re-checked proofs. Static linking (plugin as a Lake dependency of a per-workspace Mitos executable) is the simplest robust option.

### Cited Findings
- `importModules (imports : Array Import) (opts : Options) (trustLevel : UInt32 := 0) (plugins : Array Plugin := #[]) (leakEnv := false) (loadExts := false) (level := OLeanLevel.private) ... : IO Environment` — loads plugins first via `Lean.loadPlugin`, then imports. **`loadExts := true` initializes environment extensions and "may use the interpreter and thus is only safe to do after calling `enableInitializersExecution`"**; without it "the environment's constant map can be accessed", but many `CoreM`-style functions may not work properly — [Lean source: Environment.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Environment.lean)
- `withImportModules` frees compacted regions after the action and always uses `loadExts := false` — [Environment.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Environment.lean)
- `EnvironmentHeader.trustLevel`: "the kernel assumes imported constants are type correct when the trust level is greater than zero" — so a host importing untrusted .oleans must use trust level 0 and/or replay — [Environment.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Environment.lean)
- `unsafe def evalConst (α) (env) (opts) (constName) (checkMeta := true) : Except String α` — "only safe to use if the type matches the declaration's type in the environment and if `enableInitializersExecution` has been used before importing any modules"; `checkMeta` verifies referenced imported constants are marked/imported `meta`. `evalConstCheck` checks the declared type is `Expr.const typeName` but "cannot guarantee that `typeName` is in fact the name of the type α" — [Environment.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Environment.lean)
- `Lean.Kernel.Environment.replay (newConstants : HashMap Name ConstantInfo) (env : Kernel.Environment) : IO Kernel.Environment` sends constants to the kernel, throwing on rejection; **skips unsafe and partial constants** — [Lean source: Replay.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Replay.lean)
- `loadDynlib` ("Equivalent to passing `--load-dynlib=path` to lean"): "**Lean never unloads libraries**"; loading a library sharing symbols with a previously loaded one errors. `loadPlugin path initFn?` loads a shared library and runs its initializer (`initialize_<lib-name>` by default; runs the module's and its imports' `initialize`/`builtin_initialize`), "similar to passing `--plugin=path`"; env-extension registration requires running inside `withImporting`. `Dynlib.Symbol.runAsInit` is `unsafe` (no signature guarantee → UB) — [Lean source: LoadDynlib.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/LoadDynlib.lean)
- Lake config: `precompileModules` compiles each module to a native shared lib loaded on import (speeds metaprograms, enables `@[extern]` in the interpreter); `dynlibs` (loaded during elaboration, `--load-dynlib`); `plugins` (loaded as plugins with initializers, `--plugin`), e.g. `[[lean_exe]] plugins = ["Plugin:shared"]`; `needs`, `moreLeanArgs`, `weakLeanArgs` (don't affect build trace); dependencies via `require "scope" / pkg @ version` from local dirs or Git — [Lake README](https://github.com/leanprover/lean4/blob/master/src/lake/README.md)
- **Security**: Sebastian Ullrich (2020) said language-based sandboxing is "almost impossible to make 100% sound" and advised running the whole Lean process inside an external sandbox; a June 2025 "lockdown mode" proposal to block FS/network side effects by default (status unknown); `#eval` can run IO/MetaM/CommandElabM at elaboration time; `initialize` runs at import time; Lean programs can do arbitrary FFI and break memory safety — [Zulip: lockdown mode](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/lockdown.20mode.html); [Zulip: Escaping the IO monad](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/Escaping.20the.20IO.20monad.html); [Zulip: pure IO](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/pure.20IO.html) (all via search summaries; community discussion, not official policy)
- Comparator's own threat model: building the untrusted module is itself dangerous; it builds in `landrun` (Landlock-based sandbox tool) with write access only to `.lake`, exports with `lean4export`, re-checks — [comparator README](https://github.com/leanprover/comparator/blob/master/README.md)

### Inferences
- **Recommended Mitos pipeline (Lean-first):**
  1. *Workspace layout*: `mitos-core` Lake package (trusted: fact schema, `Obligation` statements, resolver, checker); `mitos-obligations` (tiny, stable, the "Challenge"); each user plugin is its own Lake package that `require`s `mitos-core` (pinned rev + toolchain) and exports a registry constant (e.g. `@[mitos_plugin] def myPlugin : Mitos.Plugin`) plus theorems named per obligation.
  2. *Build untrusted*: `lake build` the plugin inside a sandbox (container + seccomp/Landlock, no network, write only to `.lake`), as Comparator does — elaboration runs arbitrary code (`#eval`, macros, `initialize`, `run_cmd`).
  3. *Check proofs*: in a separate process, `importModules` (trustLevel 0, `loadExts := false`), look up obligation constants via `env.find?`, compare `ConstantInfo.type` against the framework statement (after `instantiateMVars`/up to syntactic equality of `Expr`, or require the plugin's theorem to have *exactly* the framework's statement constant as its type by stating obligations as `def Obligation_X (p : Plugin) : Prop` and checking `type == mkApp (const Obligation_X) (const myPlugin)`), run `collectAxioms` against an allowlist, and kernel-check via `leanchecker --fresh` or `lake check`/Comparator-style export + external kernel (nanoda) for highest assurance.
  4. *Run extractor*: either (a) statically link: generate a per-workspace `lean_exe` that imports all approved plugins and runs them in a sandboxed worker that emits facts as JSON/NDJSON, or (b) `evalConst` in a sandboxed worker after `enableInitializersExecution`. The trusted core never `loadPlugin`s untrusted code in-process (no unloading, UB risks, initializer side effects).
  5. *Record identity*: plugin assumption id = (package name, git rev, `.olean` content hash, toolchain), so every emitted edge's assumption set references an immutable artifact.
- `Kernel.Environment.replay` skipping `unsafe`/`partial` constants means extractor *code* marked `partial` is never kernel-checked — fine, because only obligation theorems need checking, but obligations must not depend on `partial`/`unsafe` defs' bodies (they're opaque to proofs anyway). Prefer total, structurally recursive extractor cores if properties of them must be proved.
- WASM sandboxing of Lean-compiled C is plausible but I found no source showing a maintained Lean→WASM toolchain in 2026; containers/Landlock (as in Comparator) are the documented path.

### Gaps
- Could not fetch the Lean reference manual or Lean FRO blog (domain blocked) to confirm current recommended APIs for running untrusted code or the status of the "lockdown mode" proposal.
- No authoritative source found on Lean→WASM compilation status in 2026.

## Q4. Declarative rule DSL embedded in Lean vs plain Lean functions for extractors

### Takeaway
Lean 4 has first-class support for embedded DSLs (`declare_syntax_cat` + `syntax` + `macro_rules` for pure macro translation, or `elab` for full control producing `Expr`), and several serious projects (Cedar, Veil, Loom, LeanSAT) show the pattern "executable semantics in Lean + DSL front-end + proofs about it". A hybrid is indicated: a small declarative rule DSL that elaborates into a deep-embedded rule AST (data the trusted core can inspect, hash, and attribute assumptions to), with an escape hatch to plain Lean functions carrying proof obligations.

### Cited Findings
- Canonical pattern: `declare_syntax_cat` introduces a grammar category, `syntax` adds productions, a `: term` syntax wraps it, and `macro_rules` maps each shape to Lean terms (recursively) — [Lean docs: Balanced Parentheses as an Embedded DSL](https://lean-lang.org/lean4/doc/syntax_example.html) (via search summary)
- Alternative: `elab` commands that convert `Syntax` → `Expr` in `MetaM`/`TermElabM`, able to throw errors (e.g. completeness checks) — [Metaprogramming in Lean 4, ch. "Embedding DSLs By Elaboration"](https://leanprover-community.github.io/lean4-metaprogramming-book/main/08_dsls.html) (via search summary)
- **Cedar** (AWS authorization language): Lean formalization with a definitional engine (`evaluate`, `satisfied`, `isAuthorized`), definitional validator, proofs, unit tests (`lake exe CedarUnitTests`), and a CLI — [cedar-lean README](https://github.com/cedar-policy/cedar-spec/blob/main/cedar-lean/README.md)
- **Veil 2.0**: "foundational" framework embedded in Lean for specifying, implementing, model-checking and proving transition systems; DSL commands such as `#check_invariants`, `#model_check`; push-button verification in decidable FOL fragments with fallback to interactive proof — [Veil README](https://github.com/verse-lab/veil/blob/main/README.md)
- **Loom**: framework for "foundational multi-modal verifiers" via a monadic shallow embedding of executable semantics; automated WP generation via Monad Transformer Algebras; used as `require "verse-lab" / "loom"` — [Loom README](https://github.com/verse-lab/loom/blob/master/README.md)
- **LeanSAT / bv_decide**: verified LRAT checker in Lean core as the trusted piece for an external SAT oracle — [Checker.lean](https://github.com/leanprover/lean4/blob/master/src/Std/Tactic/BVDecide/LRAT/Checker.lean)
- Prior-art rule DSLs outside Lean: tree-sitter-graph's graph-construction DSL over tree-sitter parse trees — [tree-sitter-graph](https://github.com/tree-sitter/tree-sitter-graph/blob/main/README.md); Glean's Angle derived predicates — [derived.md](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/derived.md); CodeQL's QL over relational DB — [about-codeql.rst](https://github.com/github/codeql/blob/main/docs/codeql/codeql-overview/about-codeql.rst)

### Inferences
- **Deep embedding wins for assumption tracking**: if rules elaborate to values of an inductive `Rule` type (pattern + emitted fact template + rule id), the trusted core can (a) give each rule a stable id/hash as an ATMS assumption, (b) prove generic theorems once over *all* rules (e.g. "every emitted fact has a source span inside the matched file", "rule output is deterministic") instead of per-plugin proofs, and (c) evaluate rules itself, so the plugin supplies only data — the strongest isolation (no user code executes). This mirrors Cedar (policy = data + verified evaluator) and Glean derived predicates.
- **Plain Lean functions** (escape hatch) give expressiveness for odd wrappers but must carry obligations (type of output, provenance/span soundness, maybe monotonicity) and run sandboxed; record them as coarser-grained assumptions (one per plugin function).
- Keep the DSL small and first-order (Datalog-ish: match → emit provides/requires) so AI agents can generate it reliably and so obligations are mostly discharged by `decide`/`simp`/generic lemmas; use `elab` (not just macros) to produce good error messages and to reject unsupported constructs at elaboration time.

### Gaps
- Did not find (in this session) Lean-embedded SQL or Datalog DSL projects to cite as direct precedent; did not inspect Cedar's/Veil's actual `syntax` definitions.

## Q5. Declaring real-world assumptions (runtime config, conventions) with provenance, expiry, and conditions

### Takeaway
Existing catalogs model declared facts as **hand-authored descriptors with source-location provenance** (Backstage `managed-by-location`, `source-location`, orphan detection) and observed facts as **time-windowed inferences** (OTel service graph with TTL'd pairing and "virtual nodes" for unobserved peers). None found combines provenance class (observed/documented/asserted), expiry, and environment conditions with retraction-aware edge labels; Mitos should model declarations as first-class ATMS assumptions with metadata.

### Cited Findings
- Backstage relations are "commonly generated based on" hand-written `spec.providesApis` / `spec.consumesApis` / `spec.dependsOn` in catalog YAML — i.e. declared, not extracted — [well-known relations](https://github.com/backstage/backstage/blob/master/docs/features/software-catalog/well-known-relations.md)
- Backstage provenance annotations: `backstage.io/managed-by-location` "points to the source from which the entity was originally fetched"; `managed-by-origin-location` differs when a location delegates; `backstage.io/orphan` marks entities whose originating location no longer references them; `backstage.io/source-location` points at source — [well-known annotations](https://github.com/backstage/backstage/blob/master/docs/features/software-catalog/well-known-annotations.md)
- OTel service graph: observed edges, labeled `client`/`server`/`connection_type`, with store `ttl`, `max_items`, unpaired/dropped span counters, and virtual nodes for uninstrumented peers; the README positions service graphs as giving "an historic view of a system's topology" because systems "change very frequently" — [servicegraphconnector README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/connector/servicegraphconnector/README.md)
- Kythe `generates`/`imputes` edges capture "extralingual process" links (codegen) that no single-language indexer sees — [Kythe schema](https://github.com/kythe/kythe/blob/master/kythe/docs/schema/schema.txt)
- Glean DB properties: arbitrary key-value metadata per DB, set by Glean or clients — [databases.md](https://github.com/facebookincubator/Glean/blob/main/glean/website/docs/databases.md)
- ATMS nogoods give a formal way to mark mutually inconsistent assumptions — [arXiv 1107.0035](https://arxiv.org/pdf/1107.0035)

### Inferences
- Suggested Lean structure for a declaration (an ATMS assumption): `{ id, fact : Fact (provides/requires/alias/route-binding), provenance : observed (source: trace/OTel query, window) | documented (url/path@rev) | asserted (author, reason), conditions : List Condition (env = prod, region, feature flag), validFrom/expiresAt, confidence?, supersedes? }`. Expired or condition-mismatched declarations simply drop out of the active environment; edges depending on them lose the corresponding label environment.
- Use OTel-style observed edges as **corroborating evidence** (separate assumption class) rather than as truth: a code-derived edge also seen in traces gets a second environment in its label; a trace-only edge is a candidate missing extractor rule. This mirrors OTel "virtual nodes" ⇔ Mitos unresolved `requires`.
- Borrow Backstage's orphan concept: when the repo/file that a declaration's provenance points to disappears or changes rev, flag the declaration as orphaned/stale rather than silently trusting it — analogous to IaC drift detection.

### Gaps
- Could not retrieve IaC drift-detection prior art (Terraform `plan -refresh-only`, driftctl) or Backstage entity-provider/processor docs in this session; no source found for a system that tracks provenance class + expiry + conditions on dependency facts together.
